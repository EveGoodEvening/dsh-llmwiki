## 结论

**没有完全达到。**

更准确的定位：

> 这是一个完成度很高的 **DeepSeek Harness 原生 llmwiki 存储、检索和结构校验底座**，但还不是 Karpathy 所说的、能够持续复利的完整 LLM Wiki 系统。

拆开判断：

| 目标 | 结论 |
|---|---|
| 能否作为 DSH 插件安装、加载、卸载、注册服务/工具/命令/提示词 | **达到** |
| 能否可靠保存不可变来源和 Markdown 页面 | **达到** |
| 能否稳定搜索、枚举、恢复和结构校验 | **基本达到** |
| 能否执行通用 ingest → query → write-back → semantic lint 复利闭环 | **未达到** |
| 是否已经证明真实模型能稳定完成这个闭环 | **未证明** |

项目本身其实没有虚假宣称。`README.md:5` 明确称其为 `storage, retrieval, and structural-integrity substrate`，`README.md:219` 也明确写着真实行为闭环尚未被证明。

## 1. llmwiki 的核心理念到底是什么

Karpathy 的 [LLM Wiki 原文](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f) 重点不是“给 Markdown 加一个搜索引擎”，而是：

### 与普通 RAG 的差异

```text
普通 RAG
问题 → 从原始文档重新检索片段 → 临时拼答案 → 对话结束后成果消失

LLM Wiki
来源 → LLM 编译进持久 wiki → 后续查询复用既有综合结果
                              ↓
                     新的有价值分析再写回 wiki
```

核心产物不是聊天答案，而是一个不断积累的知识代码库：

- 原始来源不可变，是事实依据；
- wiki 由 LLM 创建、修改、交叉链接；
- schema 约束 LLM 如何维护；
- 每次加入来源、每次提出高价值问题，都可能使 wiki 更丰富。

### 三项核心操作

#### Ingest

新来源不能只入库或建立索引。LLM 应当：

- 阅读新来源；
- 判断是新增、更新、矛盾还是无实质变化；
- 更新来源摘要页；
- 更新相关实体、概念、比较和综合页；
- 维护链接和导航；
- 记录操作；
- 保留矛盾、时间条件和来源差异。

原文强调一份来源可能更新 10–15 个页面。

#### Query

查询不只是 search：

- 从已经编译好的 wiki 导航；
- 阅读相关页面；
- 综合回答并给出引用；
- 将有长期价值的比较、分析和新联系写回 wiki。

**“好的问题也会使知识库复利”** 是这个模式的重要部分。

#### Lint

Lint 不只是 Markdown 格式检查，而是语义健康检查：

- 页面间矛盾；
- 被新来源推翻的陈旧结论；
- 缺少页面的重要概念；
- 缺少交叉链接；
- 孤立页面；
- 数据和证据缺口；
- 下一步值得研究的问题和来源。

### DeepSeek Harness 的角色

DeepSeek Harness 官方只定义插件机制，没有官方 llmwiki 行为规范：

- [Harness architecture](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md)
- [Plugin packaging](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/user/develop/basic/publish.md)
- [Tool authoring](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/cookbook/adding-a-tool.md)
- [System prompt extensions](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/core/system-prompt/README.md)

因此必须分开评估：

1. 是否正确实现了 DSH 插件；
2. 是否实现了 Karpathy 的 LLM Wiki 工作流。

前者通过，后者没有闭环。

## 2. 项目已经做得很好的部分

### DSH 集成是扎实的

`src/index.ts` 正确提供：

- `llmwiki` Cordis service；
- 9 个模型工具；
- `/wiki` 命令；
- `tool:llmwiki` 系统提示词；
- 依赖驱动加载和完整卸载生命周期。

打包 Profile E2E 覆盖：

- 真实 Loader 加载打包后的 npm tarball；
- `0.1.0-rc.6` 和 `0.1.1-rc.2` DSH 主机；
- 安装、显式启用、禁用、删除、重新安装；
- 工具、命令、提示词和持久数据不重复、不丢失。

**“是不是一个真正可加载的 DSH 插件”这一点，答案是肯定的。**

### 不可变来源设计可靠

`llmwiki_add_source`：

- 按内容 SHA-256 定址；
- 保存精确 UTF-8 参数字节；
- 内容不可修改；
- 元数据使用规范 JSON；
- 同内容去重；
- 读取时重新验证内容 hash 和字节数。

这部分符合 LLM Wiki 的 raw-source 不可变原则。

### 页面、目录与恢复能力较完整

现有模型 API 可以：

- 枚举所有来源；
- 枚举所有页面；
- 按 ID 读取来源和页面；
- 分页恢复记录；
- 搜索相关页面章节；
- 写入规范 Markdown 页面。

这已经修复了早期“模型无法知道全部 durable records”的核心缺口。

### 索引完整性已经加强

当前索引信任不再只检查格式、页面 hash 和 `state.json` hash。

`src/service.ts:984-1001` 会重新从页面构建预期索引，再逐字节比较持久化的 `search.json` 和 `state.json`。伪造一个结构合法、hash 自洽但内容并非来自页面的索引，会被判为过期并重建。

对应伪造索引回归测试也存在并通过。

### 结构 lint 比较成熟

可以检测：

- 来源 hash、元数据和字节数问题；
- 缺失来源；
- 非规范页面；
- 坏链接和逃逸链接；
- 重复标题；
- 孤立页面；
- 未引用来源；
- 索引损坏、版本不兼容、过期和伪造；
- 临时文件和符号链接。

它没有冒充语义 lint，边界描述是诚实的。

## 3. 阻断“完整 LLM Wiki”目标的主要缺口

### P1：缺少 Query → Write-back 工作流

运行时提示词只有两个工作流：

1. Evidence maintenance；
2. Semantic review。

见 `src/prompt.ts:6-19` 和 `README.md:187-203`。

没有定义：

- 如何用 wiki 回答问题；
- 如何给答案提供稳定引用；
- 什么结果值得写回；
- 如何把比较、分析和新联系归档为新页面；
- 写回之后如何更新相关页面。

搜索和 `upsert_page` 两个原语虽然存在，但模型没有被赋予 Karpathy 所定义的 Query 工作流。

因此：

> 来源可以复利，但“用户提出的好问题也能复利”尚未实现。

### P1：语义闭环没有真实模型证据

仓库存在很严格的真实代理烟测框架，但：

```text
tests/fixtures/agent-smoke/latest.json
```

当前不存在。

本次环境也没有：

- `DEEPSEEK_API_KEY`；
- `LLMWIKI_AGENT_SMOKE_MODEL`；
- `LLMWIKI_AGENT_SMOKE_NETWORK=allow`。

所以只能证明烟测框架和离线 trace 校验器正确，不能证明真实模型成功完成过当前代码的工作流。

而且现有真实烟测场景非常受控：

- 明确指定两个页面；
- 明确指定必须写入的三条句子；
- 明确指定来源和链接；
- 明确告诉模型 Harbor 被 Meridian 取代。

即使通过，它证明的也是：

> 一个模型能完成一个受控的双页面 supersession 维护和新会话恢复场景。

它没有证明：

- 模型能自主发现 10–15 个受影响页面；
- 能从新来源创建来源摘要、实体和概念页面；
- 能执行开放式语义 lint；
- 能把查询产生的新综合结论写回；
- 能在未知领域维持长期一致性。

### P1：页面写入没有乐观并发控制

`llmwiki_list_pages` 会返回页面 SHA-256，但 `llmwiki_upsert_page` 不接受：

- `expectedSha256`；
- `ifMatch`；
- 页面版本；
- 其他写入前置条件。

我执行了边界实验：

1. 两个调用者读取同一个旧页面；
2. 写入者 A 更新成功；
3. 写入者 B 基于相同旧页面更新也成功；
4. 最终 B 静默覆盖 A。

输出事实：

```text
bothStaleWritesSucceeded: true
finalWriter: B
```

同时 README 已明确说明：

- 不支持跨进程并发 writer；
- activation-local queue 不是跨进程锁。

即使在单进程中，queue 也只能串行化单次调用，不能保护跨越“读取 → 模型思考 → 写入”的完整事务。

这会直接影响 LLM Wiki 的多页面维护可靠性。

### P1：没有多页面维护事务或恢复日志

Karpathy 所说的一次 ingest 可能修改很多页面。当前每个 `upsert_page` 只是单文件原子写：

```text
page A committed
page B committed
agent/network/process interrupted
page C...N untouched
```

插件没有：

- ingest operation ID；
- intent journal；
- pending/committed 状态；
- 批量页面事务；
- 可恢复的操作日志；
- “哪些页面本应更新”的 durable 记录。

目录 catalog 可以恢复已有文件，但无法恢复一个未完成操作的意图。

`index.md` 可以被 catalog 替代；但缺少 `log.md` 或等价 journal，使中断后的语义恢复没有充分信息。

### P1：模型工具的 “Read-only” 描述与实际行为冲突

`src/tools.ts:119` 和 `src/tools.ts:195` 把：

- `llmwiki_read_source`
- `llmwiki_read_page`

描述为 `Read-only`。

但 README 又正确承认它们是 initialization-capable：缺少仓库时会创建 root、`schema.md`、`sources/`、`pages/` 和 `.index/`。

我进行了直接实验：

```text
existedBefore: false
readPage("missing") → PAGE_NOT_FOUND
之后创建了: [".index", "pages", "schema.md", "sources"]
```

所以模型实际看到的工具描述是错误的。

这不仅是术语问题。插件本身绕过：

- `ctx.fs`；
- `DSH_PERMISSION_MODE`；
- `ctx.approval`；
- filesystem intent/observation。

因此 read-only 表述会让 agent 和部署策略低估副作用。

安全做法二选一：

1. 让 readSource/readPage 真正 non-creating，未初始化时返回 `NOT_INITIALIZED`；
2. 明确改名/改描述为 initialization-capable，并保证策略层能识别其写副作用。

### P2：来源存在不等于声明有依据

页面 frontmatter 只记录来源 ID：

```yaml
sources:
  - "<sha256>"
```

服务只验证来源记录存在，不验证：

- 哪个来源支持哪段内容；
- 引用范围；
- 原文位置；
- quotation alignment；
- claim-level entailment。

这点 README 描述得很诚实，但它意味着：

> 当前系统是 source-linked，不是 claim-grounded。

在来源很多、观点矛盾或页面很长时，语义 review 的成本和误判风险会快速上升。

### P2：持久索引没有带来预期的查询性能

为阻止伪造索引，当前每次：

- search；
- status 的 index freshness 检查；
- lint 的 index 检查；

都会重新扫描并构建完整页面索引，然后才决定能否复用持久化索引。

`src/service.ts:984-993`：

```text
buildSearchIndex(paths)
→ 读取并解析全部页面
→ 生成完整 expected index
→ 与已有索引逐字节比较
```

正确性更强，但结果是：

> `.index` 现在主要是持久化完整性产物，不再是避免全量重建的廉价查询缓存。

规模增长后，search 仍然是 $O(\text{全部页面内容})$ 的前置工作。

### P2：搜索 snippet 可能不包含匹配词

`utf8Snippet()` 总是截取章节开头，而不是匹配位置附近。

我构造了一个长章节，查询词位于末尾：

```json
{
  "matched": true,
  "snippetContainsQuery": false,
  "snippet": "prefix prefix prefix prefix ..."
}
```

模型必须再读完整页面才能知道命中的原因。不会产生错误答案，但降低检索效率和可解释性。

### P2：[INFERENCE] 部分路径仍有 check/use 符号链接竞态

静态 symlink 防御测试很强，但部分路径仍采用：

```text
assertSafe/lstat
→ 随后按 pathname 调用 readFile 或 mkdir
```

例如：

- `status()` 读取 `schema.md`；
- `readPage()`；
- `upsertPage()` 的递归目录创建。

如果另一个有 root 写权限的进程在检查与使用之间替换路径，存在典型 TOCTOU 窗口。尚未执行确定性 race 注入实验，因此这是 `[INFERENCE]`，但建议补充 fd-relative/O_NOFOLLOW 或等价故障注入测试。

### P2：中断留下的部分来源不会自愈

来源写入依次创建：

1. source directory；
2. `content`；
3. `metadata.json`。

正常异常会清理目录，但进程崩溃可能留下部分记录。同内容重试时，`mkdir` 返回 `EEXIST`，随后按完整记录读取并失败。

直接实验结果：

```text
部分记录仅有 content
相同内容再次 addSource
→ SOURCE_NOT_FOUND
```

只能人工修复文件系统；模型 API 没有 repair/quarantine 能力。

### P3：示例文档使用了过期 tarball

当前包版本和 npm 发布版本均为 `0.1.3`，但：

- `examples/README.md:26`
- `examples/README.md:149`

仍使用：

```text
evegoodevening-dsh-llmwiki-0.1.1.tgz
```

这也说明现有 determinism 文档审计没有覆盖“示例 tarball 必须等于 package.json.version”。

## 5. 最终判定

### 可以这样宣传

> DeepSeek Harness 的本地优先、内容寻址、来源关联 Markdown wiki 存储和检索插件，提供可靠的结构 lint、目录恢复和模型维护原语。

### 现在还不能这样宣传

> 已完整实现 Karpathy LLM Wiki，能够稳定执行持续复利的 ingest、query、write-back 和 semantic lint。

要改变这个判定，至少需要：

1. 增加明确的 Query/answer/write-back 提示词和可观测契约；
2. 增加通用、非精确答案驱动的真实代理 eval；
3. 取得并保留当前版本的真实代理成功证据；
4. 为页面更新增加 `expectedSha256`；
5. 增加多页面操作 journal、恢复或批量提交协议；
6. 修正 read-only 副作用契约；
7. 增加更细粒度的 claim/source 定位；
8. 解决索引全量重建和匹配片段问题；
9. 修复 `examples/README.md` 的 `0.1.1` tarball。

按照仓库规则，我还更新了 `AGENTS.md` 中已经过时的索引/API结论，并记录了本次确认的依赖版本和边界行为；没有修改产品源码。
