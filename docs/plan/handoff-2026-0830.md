## 结论

**没有完全达到。**

更准确的定位是：

> 这是一个完成度很高的 **DeepSeek Harness 本地 Markdown Wiki 存储、检索和结构校验插件**，但还不是 Karpathy 所描述的完整 **LLM Wiki 持续编译与维护系统**。

分两层看：

- **作为 DSH 插件：基本达成，工程质量较强。**
- **作为“LLM 持续维护、不断复利的 Wiki”：只完成了底层基础设施，核心工作流尚未闭环。**

不能因为构建、单测、Loader/Profile E2E 全绿，就推导出“LLM Wiki 理念已经实现”。现有测试证明的是插件接口和存储路径可用，不是模型真的会持续整理知识。

## 1. 我采用的目标基准

DeepSeek Harness 上游定义的是“Everything is a Plugin”的扩展机制。我没有在上游仓库或文档中找到官方 `llmwiki` 行为规范或官方插件。

因此需要分别对照：

1. **DSH 插件契约**
   - Bundle/Profile 可安装
   - Cordis 服务注入
   - 工具、系统提示、命令注册
   - 卸载/HMR 清理
   - 发布产物真实加载

2. **Karpathy 的 LLM Wiki 理念**
   - 不只是 RAG，而是把知识持续“编译”进 Wiki
   - 三层：不可变原始资料、LLM 所有的 Wiki、指导工作流的 Schema
   - 三个核心工作流：Ingest、Query、Lint
   - 新资料到来后，LLM 应调查已有内容、更新多个页面、处理矛盾、维护交叉链接
   - Wiki 是持续复利的中间产物，而不是原始资料的另一个搜索界面

`index.md`、`log.md`、向量搜索、Obsidian 等是可选实现；**持续整合、维护和复利不是可选项，而是核心区别。**

## 3. 为什么还不能叫“完整 LLM Wiki”

### 3.1 Ingest 只是两个底层写工具，不是知识编译工作流

当前实际流程是：

```text
llmwiki_add_source
        ↓
模型自行决定做什么
        ↓
llmwiki_upsert_page
```

但 Karpathy 的 Ingest 是：

```text
保存原始资料
  ↓
调查现有 Wiki
  ↓
判断 New / Update / Contradiction / No material
  ↓
更新相关实体页、概念页、综述页
  ↓
维护交叉链接和矛盾状态
  ↓
记录本次维护
```

当前六行系统提示 `src/prompt.ts:6-12` 没有定义上述工作流。它只要求：

- 先 status；
- 先搜索再读取；
- 页面要引用 source ID；
- 新证据变化时才写；
- lint 不会修复。

这不足以让普通模型成为“纪律化的 Wiki 维护者”。

### 3.2 模型无法完整枚举已有知识

`src/tools.ts:39-214` 注册了七个工具，但没有：

- `llmwiki_list_sources`
- `llmwiki_list_pages`
- Catalog/index 浏览能力
- 未引用来源列表
- Schema 更新能力

这会产生实际的不可恢复场景：

1. 模型调用 `llmwiki_add_source`，来源已持久化。
2. 会话在写页面前中断。
3. 新会话看到 `sourceCount: 1`。
4. 但无法通过插件找出这个 source ID。
5. 搜索也找不到，因为搜索只覆盖页面。

也就是说，**持久化成功的原始资料可能在插件 API 中永久不可发现。**

`index.md` 本身不是强制要求，但缺少它之后，至少必须有等效的 catalog/list API。当前没有。

### 3.3 Schema 层是被动文件，不是有效治理层

当前：

- 初始化时创建很短的 `schema.md`；
- `llmwiki_status` 将其作为 `schemaText` 返回；
- 没有 Schema 读取/更新的独立工作流；
- 系统提示没有明确说“Schema 是组织和工作流的最高优先级约束”；
- 模型无法通过本插件与用户共同演化 Schema。

所以三层架构在文件系统上存在，但 Schema 尚未承担 Karpathy 所说的关键职责。

### 3.4 Lint 只做结构检查，不做 LLM Wiki 的语义健康检查

当前 Lint 能检测：

- 哈希不匹配；
- 引用来源不存在；
- Markdown 链接损坏；
- 页面孤立；
- 索引缺失或格式错误。

但不能检测：

- 页面间事实矛盾；
- 新来源已推翻旧结论；
- 缺少争议标记；
- 经常出现但没有独立页面的重要概念；
- 缺少的跨主题联系；
- 值得继续搜索的数据空白；
- 页面陈述是否真的受其列出的来源支持。

这些正是 Karpathy 对 Lint 的主要描述。

因此当前应该称为 **structural lint**，不是完整的 **LLM semantic lint**。

### 3.5 “Evidence-backed”目前只是“source-linked”

`llmwiki_upsert_page` 只验证：

- source ID 格式正确；
- 对应来源实际存在。

它不会验证：

- 页面中的数字、日期、引用是否出现在来源中；
- 某个段落到底由哪个来源支撑；
- 页面是否伪造结论后随便挂了一个真实 source ID。

所以当前保证的是：

> 页面至少链接了一个真实来源。

不是：

> 页面中的关键陈述已经被来源证实。

### 3.6 没有真实模型行为测试

当前 E2E 是测试代码直接依次调用七个工具，`tests/built-package.e2e.spec.ts:493` 还明确清空了 `DEEPSEEK_API_KEY`。

因此没有证明真实模型会：

1. 主动调用 status；
2. 阅读并遵循 Schema；
3. 调查已有页面；
4. 处理一份新来源；
5. 修改多个相关页面；
6. 识别和标记矛盾；
7. 在后续会话中正确查询；
8. 将高价值新分析重新写回 Wiki。

上游 DSH 测试政策也明确强调：无密钥测试证明的是 plumbing，真实模型 smoke 才证明 agent 行为。

## 4. 确认复现的实现缺陷

### P0：派生索引可以返回页面中不存在的伪造内容

涉及：

- `src/indexer.ts:275-296`
- `src/service.ts:488-508`
- `src/lint.ts:384-423`

当前“新鲜索引”只要求：

- `search.json` 结构合法；
- `state.json` 的哈希与它匹配；
- 两者携带当前页面 fingerprints。

它没有验证 sections、term frequencies、snippet text 真的是由页面重新派生的。

我实际复现了：

```text
lintErrors: 0
lintWarnings: 0
status.index.fresh: true
search("forged") 返回：
  "forged claim not present in the page"
页面实际不包含 "forged"
```

这直接破坏“搜索结果源自持久页面”的可信度。

**修复方向：**加载现有索引时重新构建并比较规范化字节，或建立等价的页面派生语义校验。仅让两个可编辑缓存文件互相验证没有可信意义。

---

### P1：页面已提交，但工具仍可能报告失败

`src/service.ts:429-438`：

1. 页面先通过原子 rename 成功提交；
2. 然后删除 `search.json` 和 `state.json`；
3. 如果索引删除失败，整个 `upsertPage` 抛错。

我复现的结果：

```text
工具结果：UNSAFE_FILESYSTEM
页面结果：新内容已经持久化
```

这会让模型误以为写入失败并重试。

而且显式删除索引并非必要：页面 fingerprints 已足以使搜索判断旧索引过期。

---

### P1：Lint 不会识别非规范化页面

`src/lint.ts:301-308` 只调用 `parsePageMarkdown()`，没有将页面重新渲染并比较原始字节。

我交换了 frontmatter 的 `title`/`summary` 顺序。页面不是规范化输出，但 Lint 没有产生 `PAGE_INVALID_MARKDOWN`。

这与错误信息“Page is not valid canonical wiki Markdown”及 README 的 canonical 声明不一致。

---

### P2：UTF-8 小范围读取可能永远不前进

对内容 `"漢"` 调用：

```text
offset = 0
limit = 1
```

实际返回：

```json
{
  "content": "",
  "byteStart": 0,
  "byteEnd": 0,
  "byteCount": 3
}
```

如果调用者用 `byteEnd` 作为下一次 offset，会形成无限循环。现有测试只验证范围合法和没有 `�`，没有验证 EOF 前必须前进。

---

### P2：空来源违反公开工具契约

工具描述声明 `content` 必须非空，但 `src/service.ts:316-324` 没有验证内容。

实际接受了空来源：

```text
id = e3b0c44298fc1c149afbf4c8996fb924...
byteCount = 0
```

空白 `origin` 也可通过，因为只拒绝长度为零，不拒绝纯空白。

---

### P2：当前安装文档使用了错误 tarball 版本

当前包版本为 `0.1.1`，实际打包文件：

```text
evegoodevening-dsh-llmwiki-0.1.1.tgz
```

但以下文档仍硬编码 `0.1.0.tgz`：

- `README.md:45`
- `README.md:63`
- `examples/README.md:22`
- `examples/README.md:136`

按文档复制执行会找不到当前产物。

## 6. 达到“真正实现 LLM Wiki”的最低补齐顺序

### 必须先做

1. 修复索引语义可信问题。
2. 增加页面和来源 catalog/list API。
3. 增加“未被任何页面引用的来源”诊断。
4. 明确 Schema 优先级和完整 Ingest/Query/Lint 工作流。
5. 加真实 DSH Agent + 模型 E2E，验证外部文件结果，而不是验证模型自述。

### 工作流应至少证明

```text
新来源
  → 保存原文
  → 枚举/搜索已有页面
  → 判断新增、更新、争议或无新增
  → 更新所有受影响页面
  → 建立交叉链接
  → 标记冲突
  → 后续新会话可查询
  → 语义审查能发现旧结论和矛盾
```

模型编排应留在 DSH agent 层，不建议让 `LlmWikiService` 自己调用模型。服务继续保持确定性；由强化后的 Schema、系统提示和可枚举工具驱动模型完成语义工作。

## 最终判定

建议对外描述为：

> **Local-first, source-linked Markdown wiki storage and retrieval plugin for DeepSeek Harness.**

暂时不建议声称：

> **A complete implementation of Karpathy’s LLM Wiki.**

如果按目标拆分评分：

- **DSH 插件集成：9/10**
- **本地持久化与确定性检索：8/10**
- **LLM Wiki 持续编译工作流：4/10**
- **语义证据与知识健康维护：3/10**

**总体：底座达成，理念闭环未达成。**
