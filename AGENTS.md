# Project Guidance

## Lessons

- As of 2026-08-16, this repository's controlled npm package name is `@evegoodevening/dsh-llmwiki`; the unscoped `dsh-llmwiki` remains a different project (`chancelu/dsh-llmwiki`) and must never be used for this implementation. npm/pnpm pack the scoped package as `evegoodevening-dsh-llmwiki-<version>.tgz`.
- Install out-of-tree DSH profile bundles with `dsh plugin --profile <name> add <package-spec>`. The command runs pnpm in the profile directory and reconciles packages declaring `dsh.bundle` into `dsh.profile.bundles`; plain `pnpm add` does not perform that activation step.
- DSH profiles intentionally set `autoInstallPeers: false`; installing this bundle therefore prints missing-peer warnings even when the running DSH supplies compatible host peers through its healed `$DSH_HOME/profiles/node_modules` fallback. Treat a successful profile boot as the compatibility proof, not `pnpm peers check`.
- As of 2026-08-23, `llmwiki_status` is strictly non-creating: it acquires safe paths without initialization, returns `initialized: false` with zero counts, `schemaText: null`, and an absent index for a missing root, and reports partial layouts without repairing them. Preserve direct service, tool, packed-package, and smoke coverage for this read-only contract.
- As of 2026-08-23, npm `@deepseek-ai/dsh` latest is `0.1.1-rc.2`. This repository declares and tests the compatible DSH service families `0.1.0-rc.6`, `0.1.0-rc.8`, and `0.1.1-rc.2`, while local development pins the complete `0.1.1-rc.2` peer closure. The packaged-profile E2E matrix boots top-level hosts `@deepseek-ai/dsh@0.1.0-rc.6` and `0.1.1-rc.2`, verifies every tool/command/prompt surface and the add-disable-remove-readd lifecycle, and asserts the actual resolved service family. A fresh install of the legacy `0.1.0-rc.6` host currently resolves its DSH service packages to `0.1.0-rc.8`; do not assume the top-level host version equals every runtime package version.
- As of 2026-08-30, DeepSeek Harness provides the plugin architecture but no official `llmwiki` behavior specification; evaluate this package separately on (1) DSH bundle/service/tool integration and (2) Karpathy's core persistent-compounding ingest/query/lint workflow. Passing Loader/profile E2E proves the first, not the second.
- As of 2026-09-03, v1 index trust is semantic rather than merely structural: status, lint, and search rebuild the page-derived expected index and byte-compare both `search.json` and `state.json`, so a forged canonical pair with current page fingerprints is rejected and search repairs it. This correctness choice also makes those freshness checks scan and rebuild the full page corpus before reusing persisted index bytes.
- As of 2026-09-03, the model-facing API can enumerate sources and pages through deterministic paginated catalogs and the repository contains a credentialed real-agent maintenance/recovery smoke harness. With no committed `tests/fixtures/agent-smoke/latest.json`, and without a query-answer/write-back workflow or general semantic-lint engine, continue describing the package as an llmwiki storage/retrieval substrate rather than a complete realization of the LLM Wiki idea.
- As of 2026-09-03, `readSource` and `readPage` still use the initializing service path: a missing-page read creates the root, `schema.md`, `sources/`, `pages/`, and `.index/` before returning `PAGE_NOT_FOUND`, despite their model-facing descriptions saying `Read-only`. Source records left partial across a process crash are not self-healing on same-content retry, and page upserts have no expected-hash precondition, so concurrent stale writers can overwrite one another.
- Package version `0.1.6` packs as `evegoodevening-dsh-llmwiki-0.1.6.tgz`; README and example commands must use the current artifact name.
- For the pinned `@deepseek-ai/dsh-agent@0.1.1-rc.2` agent smoke, use a disposable DSH profile containing the packed plugin, select plaintext unpacked JSONL session persistence (`compression: none`, `packChunks: false`), disable the first-prompt `session-title-llm` provider, and discover sessions through the `<sessions>/<project>/<session>` layout only after validating the pinned session header/profile shape.
- Keep the disposable agent-smoke runner lock exact and integrity-bearing: pin and override `@deepseek-ai/cordis@4.0.1` and `@deepseek-ai/cordis-plugin-loader@1.0.2`, and reject resolutions to Cordis `4.0.2` or Loader `1.0.3` rather than accepting lock drift.
- As of 2026-09-03, npm `@deepseek-ai/dsh` latest remains `0.1.1-rc.2`, while npm `@deepseek-ai/cordis` latest is `4.0.2` and `@deepseek-ai/cordis-plugin-loader` latest is `1.0.3`. Do not replace the agent-smoke runner's pinned `4.0.1`/`1.0.2` closure with vendor latest tags; use the packed-profile E2E boot as the compatibility proof.
- Agent-smoke evidence is valid only from a successful opted-in real model/network run and must be sanitized canonical JSON containing assertion outcomes, safe tool names, and durable IDs/hashes—not prompts, completions, content, secrets, headers, or absolute paths. Keyless/blocker preflight must leave `tests/fixtures/agent-smoke/latest.json` absent and must never create or overwrite evidence.
- npm Trusted Publishing from GitHub Actions requires a GitHub-hosted runner, `id-token: write`, npm CLI >=11.5.1, and Node >=22.14.0 (this package's stricter Node engine still applies). Bind the npm package's trusted publisher to `EveGoodEvening/dsh-llmwiki` and the exact workflow filename, not its full path. New configurations default to allowing `npm stage publish`; explicitly allow `npm publish` for direct automated releases. Use pnpm for this repository's locked install/build and npm CLI for the documented OIDC publish flow; no long-lived publish token is needed. Source: https://docs.npmjs.com/trusted-publishers/.
- `.github/workflows/publish.yml` is the direct OIDC release entry point: push a `v*` tag exactly matching `package.json`, with the npm trusted-publisher environment left empty. It pins npm 11.20.0 on Node 24 and reads pnpm from `packageManager`; keep credentialed `smoke:agent` out of release gates. Local `npm publish --dry-run` verifies packing, not GitHub OIDC authentication; the latter requires a real authorized GitHub-hosted release.
- The Linux unit suite's private read-only tmpfs proof requires root plus mount-namespace capability: `unshare --mount` fails as an ordinary user, and `mount(8)` still rejects a non-root process given only ambient `CAP_SYS_ADMIN`. The release workflow runs this suite with passwordless sudo on a full GitHub-hosted VM, preserves `PATH`/`HOME` (pnpm 11 otherwise selects another store and attempts to recreate `node_modules`), and restores generated dependency-cache ownership afterward. Local proof can use a disposable root container with `CAP_SYS_ADMIN` and mount operations permitted; never silently skip this test.
- pnpm 11 ignores `package.json.pnpm.onlyBuiltDependencies`. Disposable DSH host fixtures must declare the same explicit build allowlist as `allowBuilds` entries in their `pnpm-workspace.yaml`, following the root workspace convention; otherwise the release E2E host installs fail with `ERR_PNPM_IGNORED_BUILDS`.
- Fresh unpinned release E2E hosts failed during DSH patch watching with `hmr.registerConfig is not a function`. The disposable host matrix now reuses the frozen agent-smoke Cordis family: Cordis `4.0.1`, Group `1.0.2`, HMR `1.0.17`, Include `1.0.7`, Loader `1.0.2`, and Timer `1.1.4`. This constrains the test host; do not claim it proves compatibility with registry-latest Cordis plugins.
- npm 11.20.0 `publish --dry-run` still rejects a version already present in the registry, as observed for the already-published `0.1.3` during publishing setup. Use `npm pack --dry-run` to inspect current-version package contents without publication; a successful publish dry-run needs an unpublished version and still does not prove GitHub OIDC authorization.
- The workspace-local `.pnpm-store/` is generated pnpm cache data and is excluded by `.gitignore`; do not stage or force-add its content-addressed files in release commits.
- For the initial `0.1.4` rollout, `git push --atomic` of the new workflow branch and release tag registered `publish.yml` but produced no Actions run. A separately pushed diagnostic tag against the exact same commit started run `36568475246` and was safely rejected by the version guard before publishing. Publish the workflow-bearing branch first, confirm registration, then push the release tag separately; a first-push registration race is an inference, not a confirmed GitHub internal cause. Do not silently move an existing release tag to recover a missed event.
- This checkout's `core.sshCommand` selects the account-specific key under `~/.sb/EveGoodEvening/`. A plain `ssh -T git@github.com` uses another identity and does not diagnose this repository's Git authentication; use the configured SSH command when checking the push principal.
- Release-gate investigation reproduced a 5-second timeout in the built-entry test's real `npm run prepack` and a 10-second timeout removing a disposable DSH host in `afterEach`. `vitest.e2e.config.ts` now gives E2E tests and hooks 180 seconds, matching existing packed-package operation limits while leaving unit-test defaults and explicit 300-second profile cases unchanged. Verify with actual `CI=true GITHUB_ACTIONS=true` process environment; all 9 E2E cases and the ordinary smoke passed under those flags after this change.
- Hosted diagnostic run `36572453394` identified the actual release E2E failure: three Loader cases tried to import the package before `lib/index.js` existed, while all five packed-package cases passed. A warm local `lib/` had hidden the missing build prerequisite; the timeout fixes addressed separate local flakes. `test:e2e` must build first and use `fileParallelism: false`, because packed-package probes clean/rebuild `lib/` and temporarily hide shared `src`/`node_modules` paths. Verify from a cleaned checkout under CI flags, not just after an earlier build. Hosted run `36573424030` confirmed that the corrected cold-checkout path succeeds.
